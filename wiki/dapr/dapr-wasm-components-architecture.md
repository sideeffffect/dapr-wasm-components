> Raw: [daprd workflow GetWorkflow properties](../../raw/dapr/daprd-workflow-get-properties-v1-18.md); [go family findings](../../raw/dapr/2026-10-12-go-family-embedded-dapr-findings.md)

## Overview

Pure-wasm modules: the **interface** WIT package `dapr-wasm-components:interfaces@0.7.3` (`components/wit/`, published to OCI as `dapr-wasm-components/interfaces`; worlds `app`, `outbound`, `inbound`) and six **provider** components, split per family into an outbound and an inbound half:

- `dapr-wasm-components-wasi-http-outbound` (`components/wasi-http-outbound/`) — exports the building blocks over the Dapr HTTP API via `wasi:http` outgoing requests; portable to any WASI 0.2 runtime.
- `dapr-wasm-components-wasi-http-inbound` (`components/wasi-http-inbound/`) — exports `wasi:http/incoming-handler`, parses the HTTP app channel, calls the app's `*-callback` exports.
- `dapr-wasm-components-wasi-grpc-outbound` (`components/wasi-grpc-outbound/`) — the building blocks over the Dapr gRPC API via tonic over Spin's outbound HTTP/2 (Spin ≥ 3.4 only, see below).
- `dapr-wasm-components-wasi-grpc-inbound` (`components/wasi-grpc-inbound/`) — serves Dapr's `AppCallback` gRPC service over `wasi:http/incoming-handler` (Spin inbound h2c).
- `dapr-wasm-components-go-outbound` (`components/go-outbound/`, Go) — **Dapr itself embedded** (`github.com/dapr/dapr` v1.18 via `componentize-go`): the building blocks in-process, no sidecar; plus a private pull-based `go-events` queue.
- `dapr-wasm-components-go-inbound` (`components/go-inbound/`, Rust) — the pump that delivers go-outbound's events to the app's callbacks (`wasi:cli/run`). The go pair is one engine + one connector, not two independent providers — see [go Family](dapr-wasm-components-go-family.md).

Apps target the `app` world through the `dapr-app` SDK (`app-sdk/dapr-app/`), get composed `outbound → app → inbound` (`wac compose` with `compose.wac`, or the `compose.sh` wrapper; transports can be mixed), and run next to a Dapr sidecar (or, for the go family, alone).

## v1 → v2: why the redesign

v1 (same day) used a native wasmtime host bridging to the Dapr Rust SDK. v2 replaced it on request: the implementation must be pure wasm so *anyone* can compose against it without a custom host. The Rust SDK (tokio/tonic gRPC) cannot compile to wasm32-wasip2, so it was dropped entirely — the HTTP protocol is implemented directly. Bonus: no longer limited to what the SDK supports; the **whole** outbound API surface including alpha (lock, crypto, state query/transactions, jobs, conversation, workflow management, actors client) is covered.

## Key decisions

- **Sync WIT, blocking wasi:http.** Interfaces stay synchronous (user preference, WASI 0.2). The implementation uses `wstd`'s HTTP client with `wstd::runtime::block_on` inside sync exports — wasi:http polling blocks the guest, no async ABI needed.
- **WIT package name is `dapr-wasm-components:interfaces`** — `interface` (singular) is a reserved WIT keyword and cannot be a package name. OCI artifact names are exact and all live under one `dapr-wasm-components/` namespace (`dapr-wasm-components/interfaces`, `dapr-wasm-components/wasi-http-outbound`, …) because publishing uses `wkg oci push` with explicit references (also required for the `latest` tag — `wkg publish` only accepts semver tags). The interface uses the slash name — wkg's `<prefix><namespace>/<name>` mapping of `dapr-wasm-components:interfaces` — so the same package serves `wkg oci pull …:latest` and `wkg wit fetch` (wkg's OCI loader drops non-semver tags such as `latest`). Before 2026-10-15 every module was pushed under a flat name (`dapr-wasm-components-interfaces`, `dapr-wasm-components-wasi-http-outbound`, …); those ghcr packages are legacy and no longer updated. The providers moved to the slash scheme for consistency only — they are components, not WIT packages, so wkg's resolver never looks them up.
- **~~Outbound only.~~ Two typed directions (since 2026-06-13, package `@0.2.0`).** *Retracted:* inbound no longer goes through a plain app-served `wasi:http/incoming-handler` that the app implements by hand. Inbound flows (service invocation, pub/sub delivery, input bindings, job triggers, actor hosting, config updates, health) are delivered as typed calls on seven `*-callback` interfaces the app **exports**; a provider component parses the app channel and dispatches into them, so the app **never touches the wire** in either direction. Callback names mirror the Dapr `AppCallback` proto. Apps use the **`dapr-app`** SDK (`app-sdk/`): implement the `DaprApp` trait (every method defaulted) and `export_app!`, call Dapr via re-exported imports. See [Inbound Design](dapr-wasm-components-inbound-design.md).
- **Providers are split into outbound + inbound components (per transport).** A single provider that both *exported* the building blocks and *imported* the callbacks forms an illegal `app ↔ provider` instantiation **cycle** (the app imports the building blocks; the provider imports the callbacks) — confirmed: `wac plug` of such a pair produces a component that fails validation. Splitting makes the graph acyclic: **`outbound → app → inbound`**. `wasi-http-inbound` exports `wasi:http/incoming-handler`; the type-only `state-read`/`configuration-read`/`invocation`/`types` imports the callback interfaces pull in are satisfied from the outbound provider's exports during composition. The two directions are independent, so the gRPC suite composes `wasi-grpc-outbound` + `wasi-http-inbound`. A `wasi-grpc-inbound` provider also exists: the `wasi-grpc` crate is client-only, so it implements the `AppCallback` gRPC *server* by hand over `wasi:http/incoming-handler` (parse the gRPC length-prefix frame, prost-decode with the outbound crate's generated messages, dispatch, reply with a framed message + the `grpc-status` HTTP/2 **trailer**, which `wstd`'s `Body::from_http_body` supports). Verified over Spin's inbound h2c with `grpcurl` (`ListTopicSubscriptions`, `HealthCheck`); a daprd `--app-protocol grpc` E2E is the remaining automated check.
- **Worlds `app`, `outbound`, `inbound`.** The four-way `dapr-client`/`dapr-server` + working-name `dapr-app`/`dapr-host` was collapsed (Ondra: "settle on one nomenclature, closest to the official Dapr docs"). **`app`** = the application (imports building blocks, exports callbacks); **`outbound`** = a provider exporting the building blocks; **`inbound`** = a provider importing the callbacks. `app` is kept bare because it's pervasive Dapr vocabulary (`app-id`/`app-port`/`AppCallback`) and `host` collided with the wasm-host meaning; the provider worlds are named purely by the inbound/outbound direction (the `dapr-` prefix was dropped on 2026-06-14 — redundant inside the `dapr-wasm-components:interfaces` package, and it now matches the bare `dapr:outbound`/`dapr:inbound` package aliases in `compose.wac`). The rename is a breaking surface change, so it bumped the package `0.3.0` → `0.4.0` and ships as the **v0.4.0** release; the API-faithfulness pass below is the **v0.3.0** release (whose worlds were still `dapr-outbound`/`dapr-inbound`). (`outbound` still exports `types` etc., so no dangling `types` import remains in the composed component — the earlier `dapr-server` rationale.)
- **HTTP-faithful interface shapes**: invocation exposes verb/headers/status passthrough; state has transactions and query (possible over HTTP, impossible via the Rust SDK). (Error handling: see the **Error model** decision below — the single shared `error` variant this line used to describe was removed in `0.5.0`.)
- **Error model — no shared `error`; recoverable failures typed per function, unrecoverable ones trap (interface bumped `0.4.0` → `0.5.0`; breaking).** The original single `error` variant (7 cases: invalid-argument/not-found/permission-denied/aborted/unavailable/internal/other) was returned by *every* operation, which falsely advertised that any op could fail any way and was lossier than Dapr's actual rich errors (it discarded the `errorCode`/`reason`/details Dapr sends). Replaced by sorting failures by *who acts on them* (Ondra's framing — "if every operation can fail with the very same errors, it's becoming all meaningless"): (1) **the success type holds only the 100%-happy path** — an *expected* failure (a key not found) is still an error, never an `option` smuggled into the success slot: `state.get` → `result<get-state-response, get-error{key-not-found, state}>` (the six former `result<option<…>>` gets — state/secrets/actors-state/actors-reminder/jobs/workflow — were all converted; `lock.try-lock`/`unlock` likewise dropped their bool/status success values for `try-lock-error{not-acquired,…}`/`unlock-error{lock-does-not-exist, lock-belongs-to-others,…}`); (2) **recoverable failures** are per-interface tier-2 `variant`s (mostly `*-not-found` + `permission-denied`) and per-function tier-1 `variant`s that embed the block error as a fallback case (`state.save` → `write-error { etag-mismatch(option<string>), state(state-error) }`; `workflow` shares one `instance-error` across terminate/raise-event/pause/resume/purge, with a separate `get-error` for `get`); (3) **unrecoverable failures** (sidecar unreachable/not ready, internal sidecar/component error, timeout, I/O, any malformed-response/serialization fault) are in **no type** — the provider `panic!`s, which surfaces to the app as a **trap** (the component-model equivalent of an unchecked exception; retries/circuit-breaking belong to Dapr resiliency, not per-call handling). Modelled on **wasi-keyvalue**, whose entire error is `no-such-store | access-denied | other(string)` — it enumerates no infra cases. Inbound callbacks report graceful failure via `types.app-error { message }` (replacing the shared `error`); a callback trap also marks failure. `lock` dropped its success-position outcome types entirely — `try-lock`/`unlock` are now `result<_, try-lock-error>`/`result<_, unlock-error>` (the old `unlock-status` enum and the `bool` are gone; a tier-3 unlock failure traps). `runtime.get-metadata`/`set-metadata-label` keep only `permission-denied`. Providers classify sidecar responses best-effort (HTTP status / gRPC code → the function's variant) and panic on tier-3; the wasi-grpc `classify` maps gRPC codes to equivalent HTTP statuses so both providers share the per-block mapping. Mirrored across both outbound providers, both inbound providers, the `dapr-app` SDK, and the e2e mock/tests (the unreachable-sidecar test now asserts a trap, not a returned error).
- **Pub/sub CEL routing rules (interface bumped `0.5.0` → `0.6.0`; breaking record change).** `topic-subscription.routes: option<topic-routes>` with names from the HTTP API (`rules: [{match, path}]`, `default`). The wasi-http inbound provider puts rule paths under its reserved pub/sub prefix (no clash with invocation paths; the matched path is read back from the URL). Details: [Inbound Design §Pub/sub routing rules](dapr-wasm-components-inbound-design.md#pubsub-routing-rules-cel-060).
- **0.3.0 API-faithfulness pass** (interface bumped `0.2.0` → `0.3.0`; breaking): WIT field names mirror the **HTTP API**, even where the gRPC proto differs — bulk-get items use `value` and query results use `data` (separate records `bulk-state-item`/`query-state-item`), matching the HTTP wire even though both proto messages use `data` (each outbound provider maps its own transport). Types are made as specific as the API allows: `get-secret` returns `option` (HTTP 204 → `none`; the gRPC provider never yields `none` — no 204 analogue); `transaction-request` is flattened with `value: option` (omitted for deletes, like the actors interface) instead of reusing the save-shaped `state-item`; `publish`'s `data-content-type` is `option` (absent → the sidecar default). `conversation` models the full alpha2 surface (was a text subset) and `converse` returns the faithful `outputs → choices` structure (was a flattened list). Verified against docs.dapr.io v1.18, cross-checked against the vendored gRPC protos; mirrored across both outbound providers + the e2e mock/tests (new converse test). NB: `jobs.get` keeps the full `Job` — gRPC `GetJob` returns every field; the HTTP docs example just omits unset ones.
- **Streaming crypto as sync WIT resources (interfaces `0.5.0` → `0.6.0`; breaking, 2026-10-10).** Goal: encrypt/decrypt payloads larger than memory without WASI 0.3 and without breaking the sync-WIT rule. Shape: `resource encryptor { constructor(component, options); write(chunk) -> result<_, encrypt-error>; finish: static func(this) -> result<crypto-output, encrypt-error> }`, the same for `decryptor`, and `resource crypto-output { read(max-len) -> option<list<u8>> }` (`none` = end; chunks are never empty). `finish` *consumes* the writer, so the API is **write-all-then-read by construction** — no interleaving, so no full-duplex deadlock. Errors follow the 0.5.0 model: the function variants for recoverable failures, a trap for infra.
  - **Why not `wasi:io/streams` handles?** Passing `output-stream`/`input-stream` across the app↔provider boundary only works when both share the host's `wasi:io` (true in a `wac` composition, but it ties the WIT to `wasi:io`, gives untyped `stream-error`s instead of `encrypt-error`/`decrypt-error`, and still needs a separate `finish` to end the HTTP body and read the status). Own resources are transport-independent (the gRPC provider can buffer behind them) and testable through wasmtime's typed resource bindings.
  - **What daprd does (verified in v1.18.0 source).** HTTP: the handler pipes the request body into `encv1.Encrypt`/`Decrypt` but then `io.ReadAll`s the whole output before it answers ([source](https://github.com/dapr/dapr/blob/v1.18.0/pkg/api/http/crypto.go); the comment says this is to catch errors). The body passes through `MaxBodySizeMiddleware` (`--max-body-size`, default 4Mi), so the HTTP input is capped. gRPC: true full-duplex streaming with `seq`-checked chunks ([source](https://github.com/dapr/dapr/blob/v1.18.0/pkg/api/grpc/crypto.go)); only the per-message size is capped. So over HTTP the streaming resources save **guest** memory (app and provider hold O(chunk)), not daprd memory, and the input is still ≤ 4Mi by default.
  - **wasi-http implementation.** `streaming.rs` keeps the raw `wasi:http` 0.2 handles (outgoing body stream, `future-incoming-response`, incoming body stream) in the resource and uses blocking `wasi:io` calls — no executor has to survive between export calls (wstd's `block_on` reactor is per call). The request is handed to `outgoing-handler.handle` *before* the first body byte, so the host sends a chunked body while the guest writes. **Trap found while testing:** when the server rejects the request *before* reading the body (daprd does this for an unknown component or a bad API token) and the upload is large, wasmtime's client reports `HttpProtocolError` instead of the 400 — the early answer is lost. Fix: the constructors first check the component with `GET /v1.0/metadata` (which also checks the API token) and keep the failure for the first `write`/`finish`; a still-lost early answer traps.
  - **wasi-grpc implementation: buffered.** One tonic bidi call cannot stay in flight across export calls (one `block_on` per call; the transport collects the request body), so `write` collects in provider memory and `finish` runs one RPC. The input is now split into 1 MiB `StreamPayload`s with `seq` 0, 1, … (one-shot too), so payloads above daprd's 4Mi per-message cap work.
  - **Error mapping fixed on the way.** daprd answers an unknown component with 400 / `InvalidArgument` `ERR_CRYPTO_PROVIDER_NOT_FOUND`; the providers mapped that to `unsupported-algorithm` / `malformed-ciphertext`. Now `component-not-found` (HTTP: `errorCode`; gRPC: message match). Still open: a missing key (`ERR_CRYPTO_KEY`) and a failed decryption (`ERR_CRYPTO`) are HTTP 500 / gRPC `Internal`, so they trap.
  - **Tests.** Mock: `e2e/tests/crypto.rs` (4 MiB roundtrip in 64 KiB writes, asserts chunked uploads; 8 MiB upload to an unknown component → `component-not-found`, no hang) and kv-demo's 3 MiB roundtrip via `dapr_app::crypto_io` in `composed.rs`. Real Dapr: both suites load `crypto.dapr.localstorage` (fixed AES-256 JWK test key) and run a 3 MiB streaming roundtrip + one-shot decrypt + component-not-found from the shared scenario.
- **Interfaces 0.7.0 (breaking, 2026-10-12) — harmony with dapr4s.** Driven by the dapr4s proposal ([WASM-COMPONENTS-PROPOSAL.md](https://github.com/sideeffffect/dapr4s/blob/master/docs/WASM-COMPONENTS-PROPOSAL.md) §1, items W1–W4). Rule there: WIT models Dapr faithfully; dapr4s adapts.
  - **W1 — split by authority, along dapr4s's `ReadOnly` line only** (the name-bound `Instance` tiers stay dapr4s-only): `state-read` (get, get-bulk, query) / `state` (save, delete, execute-transaction); `secrets-read` (get-secret) / `secrets` (get-bulk-secret — enumerating a store is the wider authority); `configuration-read` (get) / `configuration` (subscribe); `jobs-read` (get) / `jobs` (schedule, delete); `workflow-read` (get) / `workflow` (start, terminate, raise-event, pause, resume, purge). Type ownership rule: the `-read` interface owns the types its functions use, the types both halves share, and the types a callback refers to (so `state-item` lives in `state-read` — `bindings-callback` uses it); types used only by the other half (`write-error`, `transaction-request`, `schedule-error`, `start-error`, `instance-error`, the `subscription` resource) stay there. `app` imports both halves, `outbound` exports both (exporting `state` without `state-read` is a WIT error: "transitively depends on an interface in incompatible ways"). **Verified: `wit-component` drops unused imports at function level** — the `e2e/apps/state-reader` fixture (calls only `state_read::get`) imports `state-read` with just `get` and no `state`; the microservice imports `secrets-read` but not `secrets`; `e2e/tests/authority.rs` reads the imports with `Component::component_type().imports()` and asserts this. **Caveat:** an interface whose *types* an exported callback uses is always imported, type-only (no functions): every app imports `state-read` and `configuration-read`. That carries no authority, but a reader of `wasm-tools component wit` output sees the name.
  - **W2 — configuration subscription is a resource.** `subscribe -> result<subscription, configuration-error>`, `resource subscription { id: func() -> string; }`; the free `unsubscribe` and `unsubscribe-error` are gone. Dropping the handle unsubscribes (`wasi-http-outbound` implements `Drop` → `GET /v1.0/configuration/{store}/{id}/unsubscribe`). **A failed unsubscribe is logged to stderr and ignored**: a destructor cannot return an error, trapping would abort the app while it only cleans up, and the cost is benign (daprd keeps pushing updates for that id to `configuration-callback` until it stops). For that the HTTP sidecar got a non-panicking `try_request`. `wasi-grpc-outbound` still traps on `subscribe`, so its resource type is an empty enum.
  - **W3 — typed `workflow-instance`**: `workflow-name`, `runtime-status` enum, `input`/`output: option<list<u8>>`, `failure: option<failure-details{error-type, message, stack-trace}>`, `properties` for the rest (e.g. `dapr.workflow.custom_status`). daprd (release-1.18 `wfengine/client.go`, release-1.19 `api/universal/workflow.go`) renders durabletask's `OrchestrationStatus` through a fixed map — `RUNNING, COMPLETED, CONTINUED_AS_NEW, FAILED, CANCELED, TERMINATED, PENDING, SUSPENDED` — and falls back to `UNKNOWN` (durabletask-go v0.12.6 also has `STALLED = 8`, which therefore shows as `UNKNOWN`). The enum has those 8 plus `unknown`; the providers match ASCII case-insensitively, and an unmatched string becomes `unknown` with the raw value kept in `properties` under `dapr.workflow.runtime_status`. Input/output/failure come from the properties `dapr.workflow.input`, `dapr.workflow.output`, `dapr.workflow.failure.{error_type,error_message,stack_trace}` (same keys in HTTP JSON and gRPC `GetWorkflowResponse.properties`; HTTP also has `workflowName`), and are removed from `properties`. 1.19 stops exposing `output` for failed instances.
  - **W4 — no `workflow-component` parameter.** Dapr has one workflow engine, the built-in component `dapr`; both providers hard-code it (the mock routes only `/v1.0/workflows/dapr/...`). `workflow-error.component-not-found` now means "the workflow engine is not available".
  - **Not done here:** W5 (workflow authoring callback) waits for WASI 0.3, per the proposal's decisions.
- **Workflow deprecation is HTTP-only (checked 2026-10-10).** The `/v1.0` workflow HTTP API is deprecated (Dapr points to the SDKs, there is no non-deprecated HTTP replacement, and 1.19 still serves it). `wasi-grpc-outbound` calls `*WorkflowBeta1` (`components/wasi-grpc-outbound/src/workflow.rs`), and those RPCs carry no `option deprecated` in the vendored v1.18 `dapr.proto` (lines ~219-238); only `*WorkflowAlpha1` does.
- **Actor hosting with gRPC outbound = mixed composition.** `AppCallback` has no actor methods, so a gRPC app that hosts actors composes `wasi-grpc-outbound` + `wasi-http-inbound` (`compose.sh --out grpc --in http`) and runs daprd with `--app-protocol http`. Rejected alternative: `SubscribeActorEventsAlpha1` (app-initiated bidi stream, `actors.proto` ~line 172) — needs a long-lived stream that a request-scoped wasm/Spin HTTP trigger cannot hold, and it is alpha.
- **JSON value convention**: HTTP state/bindings APIs carry values as JSON. Bytes that parse as JSON are embedded as-is; otherwise sent as a JSON string (UTF-8 lossy). Response strings are returned unquoted so text roundtrips.
- **Config via env** (read inside the component through `wasi:cli/environment`): `DAPR_HTTP_ENDPOINT` → `DAPR_HTTP_PORT` → `http://127.0.0.1:3500`; `DAPR_API_TOKEN` → `dapr-api-token` header.
- **Workspace split** (four Cargo workspaces): the root native workspace holds `e2e/` only; `components/` (the four providers), `app-sdk/` (the `dapr-app` SDK) and `e2e/apps/` (the demo apps) are separate **wasm-only** workspaces — guest crates don't build natively. Root `Cargo.toml` `exclude`s `components` and `e2e/apps`. Nesting the `e2e/apps/` workspace inside the `e2e` member package is fine: Cargo only reads a member's own `Cargo.toml`, never descends into sibling subdirs, so the nested `[workspace]` is independent (verified via `cargo metadata`).
- **Testing without Dapr**: `e2e/` runs the real provider in wasmtime (wasmtime-wasi-http supplies real outgoing HTTP) against a mock axum sidecar, asserting recorded requests; plus a composition test that plugs kv-demo into the provider with **wac-graph** (programmatic `wac plug`) and runs the composed command via `wasmtime_wasi::p2::bindings::Command`.
- **Testing with real Dapr** (`e2e/tests/dapr.rs`, `#[ignore]`d, CI job `dapr-e2e`): two instances of the **one** `microservice` app (originally a wstd `#[wstd::http_server]`; now a `dapr-app` app composed with `wasi-http-outbound` + `wasi-http-inbound` via `compose::plug_full`, served by `wasmtime serve -S cli --env ...`, wasmtime CLI pinned to 49.0.2 in CI) through two actual daprd 1.18 sidecars (image tag default `1.18.7`, override `DAPRD_IMAGE_TAG`) — a `publisher` and a `consumer` (role gated by a `SUBSCRIBE` env). The shared `run_mirrored_scenario` (see *E2E test mirroring* below) drives: state roundtrip + etag CAS (first-write) + delete + metadata, a `secretstores.local.file` read (existing + missing → `secret-not-found`), self- and cross-app service invocation, and a Redis-backed cross-sidecar publish→deliver→count loop; the consumer declares its subscription via `list-topic-subscriptions` (rendered to `/dapr/subscribe` by the inbound provider) and answers `/summary` invocations. Cross-sidecar name resolution: the **sqlite** nameresolution component (shared db file via daprd `--config`) — deterministic in CI, unlike mDNS. State: `state.in-memory` per sidecar. daprd quirks handled: per-sidecar `--dapr-grpc-port`/`--dapr-internal-grpc-port`, `--enable-metrics=false` (default metrics port would clash between two daprds). **Trap**: spawning daprd with piped stdio and not draining the pipes deadlocks daprd mid-startup once the pipe buffer fills — drain with reader threads. All infrastructure comes from **testcontainers**: Redis (`testcontainers-modules` redis + blocking feature) and both daprd sidecars (`GenericImage` `daprio/daprd:<tag>` — no entrypoint, binary at `/daprd`, runs as user 65532). Containerized daprd works with `.with_network("host")` (so it can dial the host-side `wasmtime serve` app channel and our test can reach its API ports) plus a bind mount of the shared dir (resources, config, sqlite nameres db) — the dir must be chmod 0777 for the non-root container user, and the sqlite connectionString must use the **container** path. wasmtime stays a host CLI (it runs the wasm under test). Future testcontainers candidates: `daprio/placement` (would unlock actors E2E) and `daprio/scheduler` (jobs triggers), both needing more app-channel protocol in the wasm services. **Trap**: the `wasmtime.dev/install.sh` script can fail resolving "latest" *and* exit 0 — pin the version and download the release tarball directly in CI.
- **OCI publishing**: `wkg oci push ghcr.io/sideeffffect/<module>:<tag>` with `org.opencontainers.image.source` annotation for repo linking. Tag `latest` on pushes to main; on GitHub releases the tag is the release version, and CI fails if it doesn't match the WIT package version in `components/wit/types.wit`. **Only the published artifacts** (`dapr-wasm-components/` + `interfaces`, `wasi-http-outbound`, `wasi-http-inbound`, `wasi-grpc-outbound`, `wasi-grpc-inbound`, `go-outbound`, `go-inbound`; were three before the 2026-06-13 provider split) are pushed — the `e2e/apps/` demo apps never are. (Earlier `dapr/client` and `dapr/kv-demo` ghcr packages were v1 leftovers, slated for deletion; v2 CI never publishes them. `wkg build --wit-dir components/wit` (formerly `wkg wit build`) still reads `wkg.toml` from the repo root CWD, so wkg.toml stays at root.)

## Repository structure (2026-06-13)

Tightened the boundary between "what we publish" and "what only exists to test it":

> *Historical snapshot (2026-06-13).* Later the same day the providers were split into `wasi-http-outbound`/`-inbound` and `wasi-grpc-outbound`/`-inbound`, the `dapr-client`/`dapr-server` worlds below were replaced by `app`/`outbound`/`inbound`, and inbound became typed — see *Key decisions* above and [Inbound Design](dapr-wasm-components-inbound-design.md).

- **`components/` = only the three published things** — `components/wit/` (the WIT package, moved from the repo-root `wit/`), `components/wasi-http/`, `components/wasi-grpc/`. The demo/fixture apps moved to **`e2e/apps/`** (their own wasm-only workspace), since they are the e2e suite's fixtures. Relative WIT paths: providers use `path: "../wit"`; demo apps use `path: "../../../components/wit"`. (On 2026-06-13 the three real-Dapr apps `order-processor`/`checkout`/`spin-demo` were consolidated into one `microservice` app — see *E2E test mirroring*; `kv-demo` remains for the mock CLI-composition test.)
- **World rename**: `imports` → **`dapr-client`** (an app imports these to *call* Dapr — the app is the client), `provider` → **`dapr-server`** (a provider exports these to *implement* the API — the component-model server side). Names now describe the *role*, not the import/export mechanism. wasmtime's `bindgen!` derives the struct name from the world, so `bindings::Provider` became `bindings::DaprServer`. World renames don't affect composition — `wac plug` matches interface identifiers (`dapr-wasm-components:interfaces/state`, …), not world names.
- **Two communication directions** (now documented in the README): these components implement **only outbound** (app → Dapr) — the `dapr-client`/`dapr-server` interfaces, transported as HTTP (wasi-http) or gRPC (wasi-grpc). **Inbound** (Dapr → app: pub/sub deliveries, bindings, invocation handlers, job/actor/config callbacks) does *not* go through any provider — the app exports `wasi:http/incoming-handler` and the sidecar calls it over a plain HTTP app channel. The two directions are orthogonal and independently configured: a wasi-grpc app calls Dapr over gRPC yet still receives events over HTTP. (A gRPC app channel is possible in Dapr but would require the app to implement the `AppCallback` gRPC service; HTTP is what every WASI 0.2 runtime can serve.)
- **CI**: builds `e2e/apps/` alongside `components/` (fmt + clippy + build for all three workspaces), validates `kv-demo.wasm` from `e2e/apps/target/`, and still publishes only the three modules. `e2e/src/lib.rs` resolves provider artifacts under `components/target/` and demo-app artifacts under `e2e/apps/target/` (the `app_path` vs `provider_artifact` split).

## Inbound path: who handles Dapr → app (investigated 2026-06-13)

> *Historical (pre-split).* This verdict described the outbound-only providers of that morning. The "route inbound through the provider" option below was then built: inbound now goes through `wasi-http-inbound` / `wasi-grpc-inbound` into the app's typed `*-callback` exports — see [Inbound Design](dapr-wasm-components-inbound-design.md).

**Claim under test**: "inbound Dapr requests go *through* the provider component (`dapr-wasm-components-wasi-http`/`-wasi-grpc`), not straight to the app." **Verdict: false for the current design** — inbound goes straight to the app; the provider is purely outbound. Proof, by `wasm-tools component wit` on the built artifacts:

- **Provider** (`dapr_wasm_components_wasi_http.wasm`): exports *only* the 14 `dapr-wasm-components:interfaces/*`; imports `wasi:http/outgoing-handler` (+ `wasi:cli`, `wasi:io`, clocks). It has **no `wasi:http/incoming-handler` export** — it physically cannot receive an inbound request.
- **App** (`microservice.wasm`, an `#[wstd::http_server]`): exports `wasi:http/incoming-handler` and `wasi:cli/run`; imports the dapr interfaces it uses + `wasi:http/types`.
- **Composed** (`wac plug` app + provider): exports `wasi:http/incoming-handler@0.2.12` (**the app's**, version-matched) and `wasi:cli/run`; the dapr interfaces are now internal (gone from the surface); imports `wasi:http/outgoing-handler@0.2.9` (**the provider's** outbound). So the host runtime delivers an inbound HTTP request to the *app's* handler; the provider only ever runs when the app makes an outbound call.

The likely source of the "goes through wasi-http" intuition is the **name collision**: inbound *does* travel over `wasi:http` (the WASI host interface, `incoming-handler` side, implemented by wasmtime/Spin) — but **not** through `dapr-wasm-components-wasi-http` (the provider component, which only uses `wasi:http`'s `outgoing-handler`). "wasi:http" (interface) ≠ "wasi-http" (provider).

### Can Dapr call the app over gRPC? (bullet "if wasi-grpc enables it")

Feasibility, researched 2026-06-13:

- **Transport — YES on Spin.** Spin's HTTP trigger serves inbound connections with `hyper_util::server::conn::auto::Builder` (`crates/trigger-http/src/server.rs`) and never calls `.http1_only()`, so it auto-detects and **accepts h2c (HTTP/2 cleartext) prior-knowledge inbound**. daprd's gRPC app channel (`--app-protocol grpc`, HTTP/2 cleartext) could therefore reach a Spin-served app at the transport layer. (Contrast wasmtime `serve`: HTTP/1.1 only — no gRPC inbound there.)
- **App/library support — NO off the shelf.** Fermyon's `wasi-grpc` 0.1.0 is **client-only**: its single public type `WasiGrpcEndpoint` wraps `wasi_hyperium::hyperium1::send_outbound_request` — there is no server, no `incoming-handler` adapter, no `AppCallback`. Serving gRPC inbound would mean implementing Dapr's `AppCallback` gRPC service (`ListTopicSubscriptions`, `OnTopicEvent`, `OnInvoke`, `ListInputBindings`, `OnBindingEvent`; protos already vendored — `dapr.proto` imports `appcallback.proto`) inside `wasi:http/incoming-handler`: route by `:path`, decode length-prefixed protobuf, reply with a gRPC frame + `grpc-status` HTTP/2 trailer. Doable two ways — hand-rolled frame parsing, or a `tonic` server (`AppCallbackServer<T>` is a `tower::Service<http::Request, http::Response>`) driven over a `wasi-hyperium` *incoming* adapter (the server-side counterpart to what `wasi-grpc` does for the client) under `spin_executor::run`. Either is a real, separate engineering effort (HTTP/2 trailers, streaming bodies under the poller, content-type negotiation).
- **Verdict**: the `wasi-grpc` crate does **not** "enable it"; the Spin runtime's transport does. gRPC inbound is buildable but is net-new code (a gRPC *server* path), not a flag flip.

### Design option: route inbound through the provider

The current "outbound-only provider, app owns `incoming-handler`" is one valid shape. The alternative the claim implies — **provider mediates inbound too** — is also coherent and is what native Dapr SDKs do: the provider would export `wasi:http/incoming-handler`, decode the Dapr inbound (CloudEvent / binding event / invocation), and call the app through new *callback* WIT interfaces the app exports (e.g. `on-topic-event`, `on-binding-event`, `on-invoke`). Benefits: symmetric abstraction, the app gets typed handlers instead of parsing HTTP/CloudEvents, and the inbound transport (HTTP vs gRPC `AppCallback`) becomes a provider detail invisible to the app. Cost: larger WIT surface (callback interfaces), more provider code, and an inversion (the *provider* becomes the HTTP/gRPC-triggered component; the app becomes a handler library). Not yet decided/implemented as of the morning of 2026-06-13; implemented the same day (split outbound/inbound providers, `*-callback` interfaces).

## E2E test mirroring (2026-06-13)

The wasi-http and wasi-grpc real-Dapr suites are **mirror images**: they run the
**same scenario** and differ only in provider + runtime + that runtime's setup.

- **One app, two roles.** `order-processor`/`checkout`/`spin-demo` were consolidated into a single `microservice` app (`e2e/apps/microservice/`), run as two instances — a `publisher` and a `consumer`. Roles are env-driven: `APP_ID`, `PEER_APP_ID`, and `SUBSCRIBE` (presence gates whether `/dapr/subscribe` returns the `orders` subscription — so the publisher doesn't also consume its own publishes). The same wasm binary is composed once per suite (`dapr.rs`: `wasi-http-outbound` + `wasi-http-inbound`; `spin.rs`: `wasi-grpc-outbound` + `wasi-http-inbound`, daprd `--app-protocol http`) and both instances run that artifact.
- **One scenario.** `e2e/tests/common/run_mirrored_scenario(Endpoints{..})` does all assertions over the two instances' HTTP surfaces: `/smoke` (JSON-value state roundtrip + etag CAS + delete + metadata), `/invoke-self`, `/publish?n=3`, poll consumer `/count` to 3 (cross-sidecar Redis pub/sub), `/publish-bulk?n=3` + poll `/count-bulk` (bulk-subscribed `orders-bulk` with a default route, delivered in batches to `on-bulk-topic-event`; since 0.6.0), `/invoke-peer` (cross-app invocation via sqlite nameres). `Endpoints.binary_state_exact` adds a `/smoke-binary` (non-JSON byte-exact) check — **only the wasi-grpc suite sets it**, since only protobuf bytes survive byte-exact; that one extra assertion is the sole scenario-level difference, and it reflects a real capability gap, not test drift.
- **What stays per-suite** (genuinely runtime-specific): how an instance is launched — `wasmtime serve -S cli --addr --env …` vs `spin up -f <manifest> --listen …` with `SPIN_OUTBOUND_H2C_PRIOR_KNOWLEDGE` and a generated `spin.toml` (DAPR_GRPC_ENDPOINT/APP_ID/PEER_APP_ID/SUBSCRIBE, allowed_outbound_hosts). Everything else — `Service` (process-group kill), `Daprd` (testcontainer), Redis, resource/config files, readiness polling, the scenario — is shared in `e2e/tests/common/`.
- **Constraint that shaped this**: Spin only triggers HTTP components, so the old CLI-command `checkout` couldn't run under Spin. Making the publisher an HTTP-triggered app (hit `GET /publish`) is what let *both* runtimes run the *same* app. The CLI-command composition path is still covered separately by the mock `composed.rs` test (kv-demo). Both suites verified green locally on 2026-06-13.

## The wasi-grpc provider (PoC, 2026-06-12)

Originally built on Fermyon's `wasi-grpc` 0.1.0 crate; since 2026-10-13 on a ~60-line `wstd` transport (`src/transport.rs`). Accepts the Spin-only constraint deliberately (see [gRPC to Dapr from Wasm](dapr-grpc-from-wasm.md) for why it isn't portable). Key decisions and traps:

- **Stack** (since 2026-10-13): tonic 0.14 (`default-features=false, features=["codegen"]` + `tonic-prost` — transport never compiles to wasm, codegen does) + `WasiGrpcService` (a `tower::Service` that collects the request body and sends it with `wstd::http::Client`; `wstd` streams the response and passes its trailers through, so tonic sees `grpc-status`) + **`wstd::runtime::block_on` as the sync bridge**, the same as the wasi-http provider. The host decides HTTP/2: Spin from `SPIN_OUTBOUND_H2C_PRIOR_KNOWLEDGE`, wasmCloud v2 from `content-type: application/grpc`. Before: `wasi-grpc` 0.1.0 + `wasi-hyperium` + `spin_executor::run`, which pinned tonic 0.13 and spin-executor 4 (`wasi-grpc` registers wakers with spin-executor 4, so our `run` had to be 4 too). Composition isolation means the provider's executor lives in its own component instance — no clash with the app's wstd reactor.
- **wasm32-wasip2 works** even though Fermyon's examples build wasip1 — that's convention, not requirement. `wasm-component-ld` semver-merges the `wasi` 0.13.1 crate's `@0.2.0` imports up to the toolchain's WASI version; the composed component carries dual-version wasi imports (provider @0.2.4/0.2.6, wstd app @0.2.9) and **Spin resolves both** via wasmtime's semver-compat export/import matching.
- **Protos vendored, codegen checked in** (like the Dapr Rust SDK): `components/wasi-grpc-outbound/proto/` holds dapr/dapr v1.18.0 protos (the `wasi-grpc-inbound` provider reuses the same generated messages via a `#[path]` module, no second codegen), `src/proto/` the generated client — generated once with **protox** (pure-Rust protoc replacement), so neither protoc nor a build script is needed. v1.18 split dapr.proto into per-block files; `dapr.proto` imports `appcallback.proto` (messages reused by streaming subscribe), so it must be in the compile set.
- **h2c is exact-match, single-authority, host-process-scoped**: `SPIN_OUTBOUND_H2C_PRIOR_KNOWLEDGE` holds ONE `host:port` compared byte-for-byte against the request URI authority; it must be set on the `spin up` process (NOT `spin up --env`, which only sets guest env), and must textually equal the `DAPR_GRPC_ENDPOINT` authority. Spin's http trigger accepts any `wasi:http/incoming-handler@0.2.x` and tolerates the app's extra `wasi:cli/run` export.
- **RPC choices**: stable names over deprecated Alpha1 where v1.18 has both (BulkPublishEvent, GetConfiguration, ScheduleJob/GetJob/DeleteJob); workflow uses the Beta1 set (Alpha1 carries `option deprecated`); lock/crypto/state-query only exist as Alpha1. Crypto's bidi streams are driven as one RPC per operation (options on the first message, payload as 1 MiB `seq`-numbered messages, half-close, reassemble by seq); the streaming WIT resources buffer behind it (see *Streaming crypto* above). JSON-in-proto payloads (job data, conversation parameters) pack as `Any(google.protobuf.Value)` (`anyjson.rs`).
- **gRPC semantic gaps vs HTTP** (documented in README): SaveState has no request-level metadata (folded into per-item metadata); GetState/GetActorState can't distinguish missing from empty (an absent key returns empty data/etag; the 0.5.0 `key-not-found` case is never produced over gRPC); InvokeService can't pass through the app's status code (200 on success, non-2xx surfaces as a gRPC error from daprd) and headers ride as gRPC metadata; no gRPC health service in daprd — `GetMetadata` is the readiness ping; error mapping (since 0.5.0): `classify` panics (trap) on tier-3 codes (`Unavailable`, `DeadlineExceeded`, `Cancelled`, `Internal`, `DataLoss`, `ResourceExhausted`, `Unknown`, `Unimplemented`) and maps the rest to an equivalent HTTP status (NotFound→404, PermissionDenied/Unauthenticated→403, AlreadyExists/Aborted→409, FailedPrecondition→412, InvalidArgument/OutOfRange→400) so both providers share the per-block mapping; a missing secret: real daprd reports a store's "not found" as a generic `ERR_SECRET_GET` on **both** transports (HTTP 500 / gRPC `Internal`; only a store returning no data gives the HTTP 204), so both outbound providers map an `ERR_SECRET_GET` whose appended store error contains "not found" (e.g. `local.file`: `secret <key> not found`) to `secret-not-found`, and gRPC also maps empty data to it; every other `ERR_SECRET_GET` is a store backend failure and traps (fixed 2026-10-10 — before, both providers trapped on a missing secret with real daprd; the shared real-Dapr scenario now checks it against `secretstores.local.file`). Same pattern for a timer on an actor type the app does not host: daprd answers `ERR_ACTOR_TIMER_CREATE` (HTTP 500 / gRPC `Internal`, message ending in `actor type not registered`), while the same condition for reminders is its own 403 `ERR_ACTOR_REMINDER_NON_HOSTED`; so all three outbound providers (wasi-http, wasi-grpc, go via `internal/daprerr`) map that one timer message to `actors-error.permission-denied` and still trap on any other `ERR_ACTOR_TIMER_CREATE` (fixed 2026-10-13, found by dapr4s's imports probe against daprd 1.17).
- **daprd gRPC quirks verified against daprd 1.18 source** (adversarial review): actor invoke metadata keys are case-sensitive — use lowercase `content-type`; daprd packs actor reminder data as `Any(google.protobuf.BytesValue)` (unpack it — raw `Any.value` is protobuf-framed) **and** the gRPC register path base64-wraps the data via Go `json.Marshal([]byte)`, so gRPC-registered reminder callbacks see base64 where HTTP-registered ones see the JSON (inherent, daprd ≤ 1.18); conversation parameters use protojson wrapper Anys (`{"@type": ".../Int64Value", "value": "100"}`) — pack the documented wrapper types, not just `Value`; `ConversationMessageOfTool.name` is a plain proto3 string (empty is wire-valid — don't reject tool-role messages); crypto accepts options+payload in one first message with `seq: 0`, capped by MaxRequestBodySize (default 4Mi) per gRPC message — hence the 1 MiB chunking.
- **E2E** (`e2e/tests/spin.rs`, CI job `spin-e2e`): the gRPC mirror of `dapr.rs` (see *E2E test mirroring*) — the same `microservice` app composed with `wasi-grpc-outbound` + `wasi-http-inbound` (gRPC out, HTTP app channel in — `wasi-grpc-inbound` has no daprd E2E yet), run as two instances by **two spin CLI processes** (each its own working dir so they don't share Spin state), against two daprd 1.18 testcontainers with Redis cross-sidecar pub/sub + sqlite name resolution. Each spin process carries `SPIN_OUTBOUND_H2C_PRIOR_KNOWLEDGE` = *its own* sidecar's gRPC authority (one authority per process — fine, since each app only dials its own sidecar). Runs the shared scenario plus a binary byte-exact state roundtrip (gRPC-only). **Trap**: `spin up` runs the server as a `spin trigger http` *subprocess* — killing the parent leaks the trigger and its port; spawn with `process_group(0)` and kill the group. **Trap**: ports in Docker's ephemeral range (32768+) can collide with stray docker-proxy mappings (testcontainers ryuk held 50053 for hours) — daprd then dies at bind; use ports below 32768. **Trap**: `pkill -f` patterns can match your own shell wrapper's command line and kill it mid-script.
- Spin CLI install: pinned tarball `github.com/spinframework/spin/releases/download/v4.2.2/spin-v4.2.2-linux-amd64.tar.gz` (was v4.0.1 until 2026-10-10) (same pin-don't-trust-latest policy as wasmtime); readiness via the built-in `/.well-known/spin/health`.

## Known limitations

- Streaming crypto saves guest memory only on the HTTP provider (daprd buffers the output; HTTP input ≤ `--max-body-size`); the gRPC provider buffers. Conversation covers the full alpha2 surface (content-part messages, tool calls/definitions, structured output, prompt-cache retention, per-token usage); configuration `subscribe` is exposed (since 0.2.0; since 0.7.0 it returns a `subscription` resource and dropping it unsubscribes; updates arrive on `configuration-callback.on-configuration-event`; `wasi-grpc-outbound` traps on subscribe). Actor hosting is HTTP-only (`AppCallback` has no actor methods), and `wasi-grpc-inbound` routes no configuration-update pushes.
- Alpha Dapr APIs can break between Dapr releases; the version-prefix map lives in [Dapr HTTP API](dapr-http-api.md).
- Binary (non-JSON) state values don't roundtrip byte-exact (JSON-string encoding).
