# dapr-wasm-components — Architecture & Decisions

> Sources: this repository (components/wit/, components/, e2e/, .github/), 2026-06-11 (v2 redesign, same day as v1); wasi-grpc provider added 2026-06-12; repository restructure + world rename 2026-06-13

## Overview

Pure-wasm modules: the **interface** WIT package `dapr-wasm-components:interfaces` (`wit/`, published to OCI as `dapr-wasm-components-interface`) and two **implementation** components exporting every interface — `dapr-wasm-components-wasi-http` (`components/wasi-http/`, the Dapr HTTP API via `wasi:http` outgoing requests, portable to any WASI 0.2 runtime) and `dapr-wasm-components-wasi-grpc` (`components/wasi-grpc/`, the Dapr gRPC API via tonic over Spin's outbound HTTP/2 — Spin ≥ 3.4 only, see below). Apps import the interfaces, get composed with an implementation (`wac plug`), and run next to a Dapr sidecar.

## v1 → v2: why the redesign

v1 (same day) used a native wasmtime host bridging to the Dapr Rust SDK. v2 replaced it on request: the implementation must be pure wasm so *anyone* can compose against it without a custom host. The Rust SDK (tokio/tonic gRPC) cannot compile to wasm32-wasip2, so it was dropped entirely — the HTTP protocol is implemented directly. Bonus: no longer limited to what the SDK supports; the **whole** outbound API surface including alpha (lock, crypto, state query/transactions, jobs, conversation, workflow management, actors client) is covered.

## Key decisions

- **Sync WIT, blocking wasi:http.** Interfaces stay synchronous (user preference, WASI 0.2). The implementation uses `wstd`'s HTTP client with `wstd::runtime::block_on` inside sync exports — wasi:http polling blocks the guest, no async ABI needed.
- **WIT package name is `dapr-wasm-components:interfaces`** — `interface` (singular) is a reserved WIT keyword and cannot be a package name. OCI artifact names are exact (`dapr-wasm-components-interface`, `dapr-wasm-components-wasi-http`) because publishing uses `wkg oci push` with explicit references (also required for the `latest` tag — `wkg publish` only accepts semver tags).
- **~~Outbound only.~~ Two typed directions (since 2026-06-13, package `@0.2.0`).** *Retracted:* inbound no longer goes through a plain app-served `wasi:http/incoming-handler` that the app implements by hand. Inbound flows (service invocation, pub/sub delivery, input bindings, job triggers, actor hosting, config updates, health) are delivered as typed calls on seven `*-callback` interfaces the app **exports**; a provider component parses the app channel and dispatches into them, so the app **never touches the wire** in either direction. Callback names mirror the Dapr `AppCallback` proto. Apps use the **`dapr-app`** SDK (`app-sdk/`): implement the `DaprApp` trait (every method defaulted) and `export_app!`, call Dapr via re-exported imports. See [Inbound Design](dapr-wasm-components-inbound-design.md).
- **Providers are split into outbound + inbound components (per transport).** A single provider that both *exported* the building blocks and *imported* the callbacks forms an illegal `app ↔ provider` instantiation **cycle** (the app imports the building blocks; the provider imports the callbacks) — confirmed: `wac plug` of such a pair produces a component that fails validation. Splitting makes the graph acyclic: **`outbound → app → inbound`**. `wasi-http-inbound` exports `wasi:http/incoming-handler`; the type-only `state`/`invocation`/`types` imports the callback interfaces pull in are satisfied from the outbound provider's exports during composition. The app channel is HTTP regardless of outbound transport (the two directions are independent), so the gRPC suite composes `wasi-grpc-outbound` + `wasi-http-inbound`. A gRPC `AppCallback` inbound provider is not yet built.
- **Worlds `app`, `dapr-outbound`, `dapr-inbound`.** The four-way `dapr-client`/`dapr-server` + working-name `dapr-app`/`dapr-host` was collapsed (Ondra: "settle on one nomenclature, closest to the official Dapr docs"). **`app`** = the application (imports building blocks, exports callbacks); **`dapr-outbound`** = a provider exporting the building blocks; **`dapr-inbound`** = a provider importing the callbacks. Chosen over client/server/host because `app` is pervasive Dapr vocabulary (`app-id`/`app-port`/`AppCallback`); `host` collided with the wasm-host meaning. (`dapr-outbound` still exports `types` etc., so no dangling `types` import remains in the composed component — the earlier `dapr-server` rationale.)
- **HTTP-faithful interface shapes**: invocation exposes verb/headers/status passthrough; state has transactions and query (possible over HTTP, impossible via the Rust SDK); errors map HTTP status classes to the `error` variant (400 invalid-argument, 401/403 permission-denied, 404 not-found, 409/412 aborted, 5xx internal, transport unavailable).
- **JSON value convention**: HTTP state/bindings APIs carry values as JSON. Bytes that parse as JSON are embedded as-is; otherwise sent as a JSON string (UTF-8 lossy). Response strings are returned unquoted so text roundtrips.
- **Config via env** (read inside the component through `wasi:cli/environment`): `DAPR_HTTP_ENDPOINT` → `DAPR_HTTP_PORT` → `http://127.0.0.1:3500`; `DAPR_API_TOKEN` → `dapr-api-token` header.
- **Workspace split** (three Cargo workspaces): the root native workspace holds `e2e/` only; `components/` (the two providers) and `e2e/apps/` (the demo apps) are separate **wasm-only** workspaces — guest crates don't build natively. Root `Cargo.toml` `exclude`s both. Nesting the `e2e/apps/` workspace inside the `e2e` member package is fine: Cargo only reads a member's own `Cargo.toml`, never descends into sibling subdirs, so the nested `[workspace]` is independent (verified via `cargo metadata`).
- **Testing without Dapr**: `e2e/` runs the real provider in wasmtime (wasmtime-wasi-http supplies real outgoing HTTP) against a mock axum sidecar, asserting recorded requests; plus a composition test that plugs kv-demo into the provider with **wac-graph** (programmatic `wac plug`) and runs the composed command via `wasmtime_wasi::p2::bindings::Command`.
- **Testing with real Dapr** (`e2e/tests/dapr.rs`, `#[ignore]`d, CI job `dapr-e2e`): two instances of the **one** `microservice` app (wstd `#[wstd::http_server]`, served by `wasmtime serve -S cli --env ...`) through two actual daprd 1.18 sidecars — a `publisher` and a `consumer` (role gated by a `SUBSCRIBE` env). The shared `run_mirrored_scenario` (see *E2E test mirroring* below) drives: state roundtrip + etag CAS (first-write) + delete + metadata, self- and cross-app service invocation, and a Redis-backed cross-sidecar publish→deliver→count loop; the consumer declares its subscription via `/dapr/subscribe` and answers `/summary` invocations. Cross-sidecar name resolution: the **sqlite** nameresolution component (shared db file via daprd `--config`) — deterministic in CI, unlike mDNS. State: `state.in-memory` per sidecar. daprd quirks handled: per-sidecar `--dapr-grpc-port`/`--dapr-internal-grpc-port`, `--enable-metrics=false` (default metrics port would clash between two daprds). **Trap**: spawning daprd with piped stdio and not draining the pipes deadlocks daprd mid-startup once the pipe buffer fills — drain with reader threads. All infrastructure comes from **testcontainers**: Redis (`testcontainers-modules` redis + blocking feature) and both daprd sidecars (`GenericImage` `daprio/daprd:<tag>` — no entrypoint, binary at `/daprd`, runs as user 65532). Containerized daprd works with `.with_network("host")` (so it can dial the host-side `wasmtime serve` app channel and our test can reach its API ports) plus a bind mount of the shared dir (resources, config, sqlite nameres db) — the dir must be chmod 0777 for the non-root container user, and the sqlite connectionString must use the **container** path. wasmtime stays a host CLI (it runs the wasm under test). Future testcontainers candidates: `daprio/placement` (would unlock actors E2E) and `daprio/scheduler` (jobs triggers), both needing more app-channel protocol in the wasm services. **Trap**: the `wasmtime.dev/install.sh` script can fail resolving "latest" *and* exit 0 — pin the version and download the release tarball directly in CI.
- **OCI publishing**: `wkg oci push ghcr.io/sideeffffect/<module>:<tag>` with `org.opencontainers.image.source` annotation for repo linking. Tag `latest` on pushes to main; on GitHub releases the tag is the release version, and CI fails if it doesn't match the WIT package version in `components/wit/types.wit`. **Only the three published artifacts** (interface + wasi-http + wasi-grpc) are pushed — the `e2e/apps/` demo apps never are. (Earlier `dapr/client` and `dapr/kv-demo` ghcr packages were v1 leftovers, slated for deletion; v2 CI never publishes them. `wkg wit build --wit-dir components/wit` still reads `wkg.toml` from the repo root CWD, so wkg.toml stays at root.)

## Repository structure (2026-06-13)

Tightened the boundary between "what we publish" and "what only exists to test it":

- **`components/` = only the three published things** — `components/wit/` (the WIT package, moved from the repo-root `wit/`), `components/wasi-http/`, `components/wasi-grpc/`. The demo/fixture apps moved to **`e2e/apps/`** (their own wasm-only workspace), since they are the e2e suite's fixtures. Relative WIT paths: providers use `path: "../wit"`; demo apps use `path: "../../../components/wit"`. (On 2026-06-13 the three real-Dapr apps `order-processor`/`checkout`/`spin-demo` were consolidated into one `microservice` app — see *E2E test mirroring*; `kv-demo` remains for the mock CLI-composition test.)
- **World rename**: `imports` → **`dapr-client`** (an app imports these to *call* Dapr — the app is the client), `provider` → **`dapr-server`** (a provider exports these to *implement* the API — the component-model server side). Names now describe the *role*, not the import/export mechanism. wasmtime's `bindgen!` derives the struct name from the world, so `bindings::Provider` became `bindings::DaprServer`. World renames don't affect composition — `wac plug` matches interface identifiers (`dapr-wasm-components:interfaces/state`, …), not world names.
- **Two communication directions** (now documented in the README): these components implement **only outbound** (app → Dapr) — the `dapr-client`/`dapr-server` interfaces, transported as HTTP (wasi-http) or gRPC (wasi-grpc). **Inbound** (Dapr → app: pub/sub deliveries, bindings, invocation handlers, job/actor/config callbacks) does *not* go through any provider — the app exports `wasi:http/incoming-handler` and the sidecar calls it over a plain HTTP app channel. The two directions are orthogonal and independently configured: a wasi-grpc app calls Dapr over gRPC yet still receives events over HTTP. (A gRPC app channel is possible in Dapr but would require the app to implement the `AppCallback` gRPC service; HTTP is what every WASI 0.2 runtime can serve.)
- **CI**: builds `e2e/apps/` alongside `components/` (fmt + clippy + build for all three workspaces), validates `kv-demo.wasm` from `e2e/apps/target/`, and still publishes only the three modules. `e2e/src/lib.rs` resolves provider artifacts under `components/target/` and demo-app artifacts under `e2e/apps/target/` (the `app_path` vs `provider_artifact` split).

## Inbound path: who handles Dapr → app (investigated 2026-06-13)

**Claim under test**: "inbound Dapr requests go *through* the provider component (`dapr-wasm-components-wasi-http`/`-wasi-grpc`), not straight to the app." **Verdict: false for the current design** — inbound goes straight to the app; the provider is purely outbound. Proof, by `wasm-tools component wit` on the built artifacts:

- **Provider** (`dapr_wasm_components_wasi_http.wasm`): exports *only* the 14 `dapr-wasm-components:interfaces/*`; imports `wasi:http/outgoing-handler` (+ `wasi:cli`, `wasi:io`, clocks). It has **no `wasi:http/incoming-handler` export** — it physically cannot receive an inbound request.
- **App** (`microservice.wasm`, an `#[wstd::http_server]`): exports `wasi:http/incoming-handler` and `wasi:cli/run`; imports the dapr interfaces it uses + `wasi:http/types`.
- **Composed** (`wac plug` app + provider): exports `wasi:http/incoming-handler@0.2.12` (**the app's**, version-matched) and `wasi:cli/run`; the dapr interfaces are now internal (gone from the surface); imports `wasi:http/outgoing-handler@0.2.9` (**the provider's** outbound). So the host runtime delivers an inbound HTTP request to the *app's* handler; the provider only ever runs when the app makes an outbound call.

The likely source of the "goes through wasi-http" intuition is the **name collision**: inbound *does* travel over `wasi:http` (the WASI host interface, `incoming-handler` side, implemented by wasmtime/Spin) — but **not** through `dapr-wasm-components-wasi-http` (the provider component, which only uses `wasi:http`'s `outgoing-handler`). "wasi:http" (interface) ≠ "wasi-http" (provider).

### Can Dapr call the app over gRPC? (bullet "if wasi-grpc enables it")

Feasibility, researched 2026-06-13:

- **Transport — YES on Spin.** Spin's HTTP trigger serves inbound connections with `hyper_util::server::conn::auto::Builder` (`crates/trigger-http/src/server.rs`) and never calls `.http1_only()`, so it auto-detects and **accepts h2c (HTTP/2 cleartext) prior-knowledge inbound**. daprd's gRPC app channel (`--app-protocol grpc`, HTTP/2 cleartext) could therefore reach a Spin-served app at the transport layer. (Contrast wasmtime `serve`: HTTP/1.1 only — no gRPC inbound there.)
- **App/library support — NO off the shelf.** Fermyon's `wasi-grpc` 0.1.0 is **client-only**: its single public type `WasiGrpcEndpoint` wraps `wasi_hyperium::hyperium1::send_outbound_request` — there is no server, no `incoming-handler` adapter, no `AppCallback`. Serving gRPC inbound would mean implementing Dapr's `AppCallback` gRPC service (`ListTopicSubscriptions`, `OnTopicEvent`, `OnInvoke`, `ListInputBindings`, `OnBindingEvent`; protos already vendored — `dapr.proto` imports `appcallback.proto`) inside `wasi:http/incoming-handler`: route by `:path`, decode length-prefixed protobuf, reply with a gRPC frame + `grpc-status` HTTP/2 trailer. Doable two ways — hand-rolled frame parsing, or a `tonic` server (`AppCallbackServer<T>` is a `tower::Service<http::Request, http::Response>`) driven over a `wasi-hyperium` *incoming* adapter (the server-side counterpart to what `wasi-grpc` does for the client) under `spin_executor::run`. Either is a real, separate engineering effort (HTTP/2 trailers, streaming bodies under the poller, content-type negotiation).
- **Verdict**: the `wasi-grpc` crate does **not** "enable it"; the Spin runtime's transport does. gRPC inbound is buildable but is net-new code (a gRPC *server* path), not a flag flip.

### Design option: route inbound through the provider

The current "outbound-only provider, app owns `incoming-handler`" is one valid shape. The alternative the claim implies — **provider mediates inbound too** — is also coherent and is what native Dapr SDKs do: the provider would export `wasi:http/incoming-handler`, decode the Dapr inbound (CloudEvent / binding event / invocation), and call the app through new *callback* WIT interfaces the app exports (e.g. `on-topic-event`, `on-binding-event`, `on-invoke`). Benefits: symmetric abstraction, the app gets typed handlers instead of parsing HTTP/CloudEvents, and the inbound transport (HTTP vs gRPC `AppCallback`) becomes a provider detail invisible to the app. Cost: larger WIT surface (callback interfaces), more provider code, and an inversion (the *provider* becomes the HTTP/gRPC-triggered component; the app becomes a handler library). Not yet decided/implemented as of 2026-06-13.

## E2E test mirroring (2026-06-13)

The wasi-http and wasi-grpc real-Dapr suites are **mirror images**: they run the
**same scenario** and differ only in provider + runtime + that runtime's setup.

- **One app, two roles.** `order-processor`/`checkout`/`spin-demo` were consolidated into a single `microservice` app (`e2e/apps/microservice/`), run as two instances — a `publisher` and a `consumer`. Roles are env-driven: `APP_ID`, `PEER_APP_ID`, and `SUBSCRIBE` (presence gates whether `/dapr/subscribe` returns the `orders` subscription — so the publisher doesn't also consume its own publishes). The same wasm binary is composed once per provider and both instances run that artifact.
- **One scenario.** `e2e/tests/common/run_mirrored_scenario(Endpoints{..})` does all assertions over the two instances' HTTP surfaces: `/smoke` (JSON-value state roundtrip + etag CAS + delete + metadata), `/invoke-self`, `/publish?n=3`, poll consumer `/count` to 3 (cross-sidecar Redis pub/sub), `/invoke-peer` (cross-app invocation via sqlite nameres). `Endpoints.binary_state_exact` adds a `/smoke-binary` (non-JSON byte-exact) check — **only the wasi-grpc suite sets it**, since only protobuf bytes survive byte-exact; that one extra assertion is the sole scenario-level difference, and it reflects a real capability gap, not test drift.
- **What stays per-suite** (genuinely runtime-specific): how an instance is launched — `wasmtime serve -S cli --addr --env …` vs `spin up -f <manifest> --listen …` with `SPIN_OUTBOUND_H2C_PRIOR_KNOWLEDGE` and a generated `spin.toml` (DAPR_GRPC_ENDPOINT/APP_ID/PEER_APP_ID/SUBSCRIBE, allowed_outbound_hosts). Everything else — `Service` (process-group kill), `Daprd` (testcontainer), Redis, resource/config files, readiness polling, the scenario — is shared in `e2e/tests/common/`.
- **Constraint that shaped this**: Spin only triggers HTTP components, so the old CLI-command `checkout` couldn't run under Spin. Making the publisher an HTTP-triggered app (hit `GET /publish`) is what let *both* runtimes run the *same* app. The CLI-command composition path is still covered separately by the mock `composed.rs` test (kv-demo). Both suites verified green locally on 2026-06-13.

## The wasi-grpc provider (PoC, 2026-06-12)

Built on Fermyon's `wasi-grpc` 0.1.0 crate, accepting the Spin-only constraint deliberately (see [gRPC to Dapr from Wasm](dapr-grpc-from-wasm.md) for why it isn't portable). Key decisions and traps:

- **Stack**: tonic 0.13.1 (`default-features=false, features=["codegen","prost"]` — transport never compiles to wasm, codegen does) + `wasi-grpc` (a `tower::Service` bridging tonic to `wasi-hyperium`'s wasi:http outgoing path) + **`spin_executor::run` as the sync bridge** — it's pure `wasi:io/poll` polling (deps: futures, once_cell, wasi=0.13.1; no Spin host imports), the exact analogue of wstd's `block_on` in the wasi-http provider. Composition isolation means the provider's executor lives in its own component instance — no clash with the app's wstd reactor.
- **wasm32-wasip2 works** even though Fermyon's examples build wasip1 — that's convention, not requirement. `wasm-component-ld` semver-merges the `wasi` 0.13.1 crate's `@0.2.0` imports up to the toolchain's WASI version; the composed component carries dual-version wasi imports (provider @0.2.4/0.2.6, wstd app @0.2.9) and **Spin resolves both** via wasmtime's semver-compat export/import matching.
- **Protos vendored, codegen checked in** (like the Dapr Rust SDK): `components/wasi-grpc/proto/` holds dapr/dapr v1.18.0 protos, `src/proto/` the generated client — generated once with **protox** (pure-Rust protoc replacement), so neither protoc nor a build script is needed. v1.18 split dapr.proto into per-block files; `dapr.proto` imports `appcallback.proto` (messages reused by streaming subscribe), so it must be in the compile set.
- **h2c is exact-match, single-authority, host-process-scoped**: `SPIN_OUTBOUND_H2C_PRIOR_KNOWLEDGE` holds ONE `host:port` compared byte-for-byte against the request URI authority; it must be set on the `spin up` process (NOT `spin up --env`, which only sets guest env), and must textually equal the `DAPR_GRPC_ENDPOINT` authority. Spin's http trigger accepts any `wasi:http/incoming-handler@0.2.x` and tolerates the app's extra `wasi:cli/run` export.
- **RPC choices**: stable names over deprecated Alpha1 where v1.18 has both (BulkPublishEvent, GetConfiguration, ScheduleJob/GetJob/DeleteJob); workflow uses the Beta1 set (Alpha1 carries `option deprecated`); lock/crypto/state-query only exist as Alpha1. Crypto's bidi streams are driven one-shot (single request message carrying options + whole payload, then half-close, reassemble by seq). JSON-in-proto payloads (job data, conversation parameters) pack as `Any(google.protobuf.Value)` (`anyjson.rs`).
- **gRPC semantic gaps vs HTTP** (documented in README): SaveState has no request-level metadata (folded into per-item metadata); GetState/GetActorState can't distinguish missing from empty (empty data+etag → `none`); InvokeService can't pass through the app's status code (200 on success, non-2xx → `error`) and headers ride as gRPC metadata; no gRPC health service in daprd — `GetMetadata` is the readiness ping; `grpc-status` codes map 1:1 to the WIT error variant (cleaner than HTTP status classes); a missing secret surfaces as `internal` (ERR_SECRET_GET), not `not-found`.
- **daprd gRPC quirks verified against daprd 1.18 source** (adversarial review): actor invoke metadata keys are case-sensitive — use lowercase `content-type`; daprd packs actor reminder data as `Any(google.protobuf.BytesValue)` (unpack it — raw `Any.value` is protobuf-framed) **and** the gRPC register path base64-wraps the data via Go `json.Marshal([]byte)`, so gRPC-registered reminder callbacks see base64 where HTTP-registered ones see the JSON (inherent, daprd ≤ 1.18); conversation parameters use protojson wrapper Anys (`{"@type": ".../Int64Value", "value": "100"}`) — pack the documented wrapper types, not just `Value`; `ConversationMessageOfTool.name` is a plain proto3 string (empty is wire-valid — don't reject tool-role messages); crypto accepts options+payload in one first message with `seq: 0`, capped by MaxRequestBodySize (default 4Mi) per gRPC message.
- **E2E** (`e2e/tests/spin.rs`, CI job `spin-e2e`): the gRPC mirror of `dapr.rs` (see *E2E test mirroring*) — the same `microservice` app composed with the wasi-grpc provider, run as two instances by **two spin CLI processes** (each its own working dir so they don't share Spin state), against two daprd 1.18 testcontainers with Redis cross-sidecar pub/sub + sqlite name resolution. Each spin process carries `SPIN_OUTBOUND_H2C_PRIOR_KNOWLEDGE` = *its own* sidecar's gRPC authority (one authority per process — fine, since each app only dials its own sidecar). Runs the shared scenario plus a binary byte-exact state roundtrip (gRPC-only). **Trap**: `spin up` runs the server as a `spin trigger http` *subprocess* — killing the parent leaks the trigger and its port; spawn with `process_group(0)` and kill the group. **Trap**: ports in Docker's ephemeral range (32768+) can collide with stray docker-proxy mappings (testcontainers ryuk held 50053 for hours) — daprd then dies at bind; use ports below 32768. **Trap**: `pkill -f` patterns can match your own shell wrapper's command line and kill it mid-script.
- Spin CLI install: pinned tarball `github.com/spinframework/spin/releases/download/v4.0.1/spin-v4.0.1-linux-amd64.tar.gz` (same pin-don't-trust-latest policy as wasmtime); readiness via the built-in `/.well-known/spin/health`.

## Known limitations

- Crypto is one-shot (no streaming); conversation is the alpha2 text subset (no tool calls); configuration subscribe not exposed.
- Alpha Dapr APIs can break between Dapr releases; the version-prefix map lives in [Dapr HTTP API](dapr-http-api.md).
- Binary (non-JSON) state values don't roundtrip byte-exact (JSON-string encoding).
